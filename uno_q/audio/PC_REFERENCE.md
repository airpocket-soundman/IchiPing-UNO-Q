# PC基準音 → UNO Qマイク：準備用テスト

現在は**ローカル実装・無発音テストのみ**。実機配備、PC再生、録音は未実施。
推論アプリではなく、マイク経路を独立に検証するbring-up用ツール。

## 無発音で準備

リポジトリのルートで実行:

```powershell
python uno_q/audio/pc-reference-test.py
```

`uno_q/audio/local-runs/<run-id>/` に基準WAVとreport.jsonを作るだけ。
SSH、ボード操作、再生APIは呼ばない。このフォルダはGit対象外。
音源は440 Hz、100 ms、前後5 msフェード、stereo PCM16、ピーク3/32768 FS。
微小振幅で量子化が粗いため、この段階の音質校正用の理想波形ではない。

## 将来、実際に試験するときだけ

PCの既定の再生先が意図したスピーカーであること、Windows音量が低いこと、
UNO Qのマイクがその音を拾える位置にあることを確認する。自動で音量変更しない。

```powershell
python uno_q/audio/pc-reference-test.py --execute
```

秘密鍵はローカルの `uno_q/test_ssh/unoq_test_ed25519`、sudoパスワードは実行時入力。
パスワードは引数・ログ・ファイルに保存しない。初回のSSHホスト鍵は事前確認が必要。
新しいスクリプト群をボードの一意な `/var/tmp/` フォルダへ配備する。
既存カーネル/DT/サービスは変更せず、カードが未準備なら失敗して止まる。
自動DSP復旧やカーネル更新は行わない。

## 録音と発音の順序

1. USB識別（2341:0078 / 指定serial）、音声カード、競合プロセスを確認。
2. ボードの独立500 msリセット期限を、音声経路の有効化より前に設定。
3. UNO Q側はゼロPCMだけを再生して共有クロックを作り、100 ms立ち上がり待ち。
4. ステレオ録音を開始し、ALSA RUNNING後にrun-id付きREADYをPCへ通知。
5. PCは30 msの先行録音余白を置いて100 msの基準音を再生する。
6. ボードのリセット後も回収を最大120秒試み、そのrun-idの録音だけを保存。

**録音は発音より前に始まり、発音後も継続する構成**。ただし安全期限内に
得られる録音は通常数百msの部分データであり、秒単位の録音は保証しない。
SSH通知・Windows再生開始には遅延がある。命令時刻を実際の発音時刻とは扱わない。
回収後、440 Hz包絡の前後に余白があるかを検査する。音が欠けた疑い、検出不能、
短い録音はタイミング未成立と記録し、音質合格にはしない。自動で期限を延ばさない。

PC側は非ループ再生をfinallyで停止し、親プロセスも子を500 msで打ち切る。
これはOS遅延を含めた厳密な音響時間の保証ではない。

## 重要な制約

- マイク単独のクロック開始でアンプ雑音を再現したため、UNO Q側のゼロPCMは必要。
  ゼロデータでもMAX98357Aの物理的な消音保証にはならない。SD回路は変更しない。
- PC基準音以外にUNO Qアンプの雑音が混入する場合、マイクの独立評価は成立しない。
  長時間録音や確実な独立評価は、アンプを物理的に無効化できる条件で別途設計する。
- デフォルト音声デバイスの遅延、PCの音量、部屋の雑音は未校正。
- 録音の再生は自動で行わない。

出力: `reference.wav`、`capture-stereo-s16.raw`、`capture-stereo.wav`、
`capture-left.wav`、`report.json`（ボードログ、カーネルhash、解析、タイミング判定）。
一意なrun-idにより古い録音を今回の結果として使用しない。
