# UNO Q I²S発音不良：無負荷信号監査（2026-09-11）

## 結論

現行の再生専用S32_LE試験では、定常部のクロック・標準I²S形式・送信PCMは正常に観測された。一方、**WSが止まった後もBCLKが約1.2〜1.4 ms動き続ける**。MAX98357Aのメーカーが警告する停止条件に該当するため、常時有効のアンプと組み合わせる際の具体的な問題候補である。

これはUNO Qハード全般の故障を示す結果ではなく、このプロジェクトのLinux/ALSA/MI2S開始停止制御とアンプ有効化方法の適合性の問題。アンプを外した試験なので、過去の発音不良の全原因が確定したわけではない。マイク・アンプが元プロジェクトでは動作することはユーザー確認情報として扱い、部品交換よりUNO Q側の制御を優先調査する。

## 実測結果

| 検査 | ゼロPCM | サインPCM |
|---|---:|---:|
| 保存サンプル数 | 250,000,000 / 指定と一致 | 250,000,000 / 指定と一致 |
| BCLK平均周波数 | 3,071,997.23 Hz | 3,071,996.27 Hz |
| WS平均周波数 | 32 BCLK/半周期を確認 | 47,999.944 Hz |
| WS半周期のクロック数 | 59,629区間すべて32 | 59,131区間すべて32 |
| BCLK周期 | 16または17取得サンプルのみ | 同左 |
| DATA | 全取得期間ゼロ | 左右各24,000サンプル、基準PCMと不一致0 |
| BCLK開始→最初のWS変化 | 4.59912 ms | 4.32342 ms |
| 最後のWS変化→最後のBCLK立上り | 1.41846 ms | 1.23260 ms |
| BCLK観測区間 | 627.15356 ms | 621.50466 ms |

50 MS/sの時間分解能は20 ns。BCLK周期の中央値の逆数を使うと3.125 MHzになるが、これは量子化の偏り。多数周期の全時間から求めた平均は約3.072 MHzであり、周波数異常ではない。ロジアナの絶対周波数校正まではしていない。

サイン試験のWS/DATA変化は、最寄りのBCLK立上りから前後とも最小160 ns離れて観測された。標準I²S（WS Low=左、MSBはWS変化の1クロック後、立上り取得）で復号し、短い/長いスロット、クロック欠落、立上りと同時のDATA/WS変化は0。20 ns分解能では細かなジッタ、電圧、立上り品質の合格判定はできない。

### PCM比較の位置合わせと制限

最初の非ゼロサンプルを基準の最初の非ゼロ（frame 4802）に対応させた。観測左のframe 7541から、先行2739 framesが加わったと推定。右は最初の不完全左スロットが捨てられているため2740 frames。最良相関区間の自動探索はしていない。

この明示した位置合わせで左右各24,000 framesが完全一致し、負値も各2395点一致。比較範囲外はゼロ。先行ゼロは区別不能なのでPCMの開始時刻・DSP遅延の厳密値は未確定。左右が同じ信号のため左右入替えの識別はできない。今回の440 Hz試験値での一致を、任意振幅・周波数・同時録音条件の合格へ一般化しない。

## 前回の「異常フレーム」の扱いを訂正

16ch・ソフトウェアトリガー使用時は約62.5 ms周期で異常が現れた。Sipeedソースでは10%のプリトリガーを設定するため、CLI表示とSRチャンク合計の10,000,000 samples差には説明がつく。ただし要求数との差や周期異常の全原因は未確定。

4ch・トリガーなしでは保存数・全フレームとも整合した。**前回の異常をUNO Q由来のビット欠落とする根拠はない**。チャンネル数とトリガーの2条件を同時に変更したため、どちらの影響かはまだ分離できていない。ベンダーCSV出力の時刻/重複処理にも不明点があったため、SRのサンプル番号から直接CSV化し、チャンク境界と末尾保持をオフラインテストで確認した。

## 公開資料との照合

1. [MAX98357A/Bメーカー・データシート（Adafruit配布）](https://cdn-shop.adafruit.com/product-files/3006/MAX98357A-MAX98357B.pdf)：pp.6–7、16、19。48 kHz/64 BCLKは対応形式。High最小1.3 V、Low最大0.6 Vで、1.8 Vロジックという設計自体は不適合ではない。ただし今回の無負荷0.9 Vしきい値ではアンプ端での電圧余裕を検証していない。
2. [Analog Devices公式FAQ：DC output on speaker for MAX98357](https://ez.analog.com/audio/a/documents/do11587/dc-output-on-speaker-for-max98357)：有効中にBCLKを残してLRCLKを止めるとDC出力が残り得る。LRCLK停止前にSDをLow、再有効化前にLRCLKが必要としている。今回の停止順序はこの警告と一致するが、アンプ未接続なのでDCそのものは測定していない。
3. [ArduinoカーネルのMAX98357ドライバー](https://github.com/arduino/linux-qcom/blob/0dd6551ae96b78024086e72339fefbef6fcc604b/sound/soc/codecs/max98357a.c)：sdmode GPIOは任意。未設定ならtriggerで制御せず戻る。本プロジェクトのDTもsdmode-gpiosなしなので、Linuxからアンプを停止順序に合わせて無効化できない。
4. [Arduinoカーネルのsm8250 machine driver](https://github.com/arduino/linux-qcom/blob/0dd6551ae96b78024086e72339fefbef6fcc604b/sound/soc/qcom/sm8250.c) とローカルclock-stopパッチ：BCLKのstartup/shutdown制御とDSPのWS開始停止は別段階。既存パッチ版でも、今回観測したBCLKだけの区間は残る。
5. [Sipeed使用版の取得実装](https://github.com/sipeed/libsigrok/blob/0c36240d8dbb2b2e06f9a9ba9d889a9be752536c/src/hardware/sipeed-slogic-analyzer/protocol.c)：プリトリガーとUSB転送キューを確認。

## 次の対策・検証

- 最優先はアンプの有効化順序。SDを未接続で常時有効にする前提を、このUNO Q構成については見直す。SD制御の配線・電圧・GPIOを確定し、WS停止前に確実に無効化、BCLK/WS/DATA安定後に有効化する。単にGPIOを追加するだけで順序保証とせず、SDを含む同時波形で確認する。
- 別案は有効中にBCLK/WSを途切れさせずゼロPCMを継続する方式。ただし障害時のミュートまで含めた設計が必要。
- まず無負荷で再生＋録音開始時のクロック変化を調べる。今回の再生専用合格を、プロジェクトの全二重動作へ一般化しない。
- アンプを再接続する前に有効化/停止制御を確立する。その後、アンプ端で電圧・GND・負荷による信号品質をオシロ確認し、独立した録音器で発音を評価する。INMP441経由の録音だけで発音側を判定しない。
- この調査ではファーム/DT/アンプ配線を変更していない。ボード再起動後、ALSAカードと再生・録音ルート双方offを確認済み。

### 有効な再取得の結果

- `duplex-sine-4ch-repeat.sr`：指定どおり250,000,000 samples、5秒、125,000,000 USB bytes（4chパック形式）、80 transfers。保存完了後に解析。
- BCLK平均3,071,996.84 Hz。周期は16/17サンプルのみ、WS半周期97,399区間すべて32 BCLK。
- 標準I²S復号で短長スロット・クロック欠落・立上り同時変化すべて0。
- 左右各24,000 samplesで基準sine.rawと不一致0、負値は各2395点一致、比較範囲外は全ゼロ。非ゼロ開始による明示的な位置合わせは再生専用時と同じ（左2739、右2740先行frames）。
- BCLK観測1.01828718秒、WS開始前3.70394ms。最後のWS変化から最後のBCLK立上りまでは9.28µsで、通常の半フレーム約10.42µs以内。この値を再生専用時の1.2–1.4msの無WS継続と同一視しない。録音中はWS/BCLKが維持され、途中の再生終了による長いWS停止は見られなかった。
- マイク未接続の録音 `/var/tmp/ichiping-instrument-duplex-WFES9q.raw` は61,440 bytes / 15,360 stereo frames、全ゼロ。マイク動作の合格ではない。

### 不採用の初回記録と復旧

初回 `duplex-sine-4ch.sr` はエージェントが最終保存前に読み出し、Windowsのファイルロックで最終renameが失敗した。180,355,072 samplesの途中記録であり、判定に不使用。削除せず原因を明記して保持。

その試験後の再起動ではALSAカードが現れず、`qcom-sm6115-lpass-lpi-pinctrl: Failed to get clk 'audio'` によるdeferred probeを確認。ADSPはrunningだが音声初期化は未完了だった。aplay/arecordがないこと、remoteproc1のname=adspを確認し、無負荷でADSPのみstop/startするとALSAカードが復旧した。その後上記再取得を実施。起動・再起動時の初期化不安定は別問題として残る。

最終再起動後はALSAカードあり、再生/録音ルートoffを確認。boot ID `843c2a8e-ceb4-4588-a7ac-e39f846a5970`。

### 診断の更新

今回の条件では「録音を開始すると出力データが崩れる」は支持されなかった。現在のドライバーとS32形式で、無負荷のデジタル伝送は再生単独・同時録音とも正しく観測された。
ただし、元の発音試験からドライバー/PCM形式/開始手順も変化しているため、過去の不具合を単一原因へ断定できない。
次はSDを含む開始停止制御を確立したうえで、アンプ端の負荷時波形と独立録音で発音を確認する段階。無負荷のソフトウェア試験を増やすだけでは、残る電気的/音響的な原因を確定できない。
