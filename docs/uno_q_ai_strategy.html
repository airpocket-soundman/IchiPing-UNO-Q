精度優先AI方針

UNO Q版はMCU向けの小型化を主目的にせず、QRB2210 / Debian上で推論する。モデル容量、演算量、FP32利用を許容し、未知の収録条件に対する精度を最優先する。

1. 実機資源と運用上限

項目2026-08-21実測候補モデルの基準
CPUARM64 4コア、最大2.016 GHz特徴量生成後のwarm推論 p95を1,000 ms以下
RAM3.6 GiB搭載、通常時約3.0 GiB available、1.8 GiB swap推論アプリ全体のpeak RSSを1.5 GiB以下。swap依存は禁止
ストレージルート約2.9 GiB空き配布モデル一式500 MiB以下
現行XL約0.7 MiB、約10万パラメータ級UNO Qに対して小さすぎるため比較用baselineとする

上限までモデルを大きくすること自体は合格条件ではない。学習データ量に対して過大なモデルは過学習し得るため、外部評価が改善しない候補は小さいモデルより優先しない。

2. モデル探索

  1. 既存32-class XLをbaselineとして、同一データ・同一splitで再現する。
  2. 約100万、500万、1,000万〜3,000万パラメータ級へ段階的に拡張する。
  3. 既存の1D spectrum枝に加え、時間情報を残すlog-mel / multi-resolution STFT枝を比較する。
  4. 単一モデルの拡張が飽和したら、異なるseedまたは特徴量の2〜3モデルensembleと複数ping投票を比較する。
  5. FP32 ONNX Runtimeを基準に選定し、FP16・INT8は評価精度が統計的に同等な場合だけ採用する。

3. 精度の合格基準

ランダム分割の最高値だけで選ばない。収録日、背景雑音、マイク／スピーカ位置をgroupとして分離し、未知条件を模擬する。

指標選定での扱い
32-state accuracy / macro-F1主要指標。複数seedの平均とばらつきを記録
worst-class recall一部状態だけを犠牲にするモデルを排除
環境別accuracy収録日、雑音、位置ごとの最低値を比較
confidence calibrationMatrixの信頼度表示と再試行判定に使用
実機資源p95 latency、peak RSS、モデル容量を精度表と併記
採用規則: 制約内の候補から未知条件のmacro-F1を最優先し、差が評価ばらつき以内ならworst-class recall、次に小さいRSSと短いlatencyで決める。

4. UNO Q実機ベンチ

uno_q/tools/benchmark_onnx.pyはONNXのload時間、warm推論p50/p95/p99、peak RSS、モデル容量をJSONで出力する。

python3 uno_q/tools/benchmark_onnx.py model.onnx --shape 1,1,1024

音響経路確定後は合成入力だけでなく、保存した実pingを使うend-to-endベンチを追加する。
